Full suite: 4,003 tests (up from 3,951). Earlier work: **IMDb Metadata Recovery**. A new, deliberately separate Crew-only `/database manage` action, **Recover Missing IMDb Links**, complements IMDb Metadata Refresh (below) for the case Refresh can never reach: a suggestion with no usable IMDb identifier at all (added by plain title, with no link). Recovery finds those suggestions, searches OMDb for the right title using each suggestion's stored title and (when known) release year via a new `ImdbMetadataService.search_titles()`, and -- only once a WASH Crew member explicitly approves a specific candidate -- saves the identifier and immediately hands off to `ImdbMetadataRefreshService.refresh_one()` (made public for this reuse) to populate the rest, exactly as if a normal Refresh IMDb Metadata run had touched that suggestion. Scope mirrors Refresh exactly (**Recover This Collection**/**Recover All Collections**, reusing `resolve_refreshable_databases` via a thin `resolve_recoverable_databases` alias so guild/active scoping can never drift between the two workflows), gated behind the same kind of confirmation screen (scope, collection count, missing-suggestion count, and an explicit disclosure that every match requires approval and an existing identifier is never overwritten). Matching is deliberately conservative: a search scoped to the suggestion's stored year returning exactly one result is shown as a single high-confidence match for confirmation; more than one plausible result is shown as a selection list distinguished by title/year/type (choosing one only proposes it -- the same explicit-Accept confirmation screen still gates the save); zero results at the stored year falls back to a title-only search rather than concluding "no match," but every fallback candidate is visibly flagged with a year-mismatch note so nothing is silently assumed; genuinely nothing found offers only Search Again/Skip/Cancel Recovery. Every screen offers **Accept**, **Skip** (never permanent -- `missing_suggestions()` recomputes fresh from current data on every scan, so a skipped suggestion resurfaces on the next run), **Search Again** (a modal accepting a manually typed title optionally followed by a year -- `parse_recovery_search_query()` splits "The Thing 1982" or "The Thing (1982)" into title/year identically), and **Cancel Recovery** (aborts the whole run; every suggestion not yet reached is reported Cancelled, a fourth outcome bucket alongside Matched/Skipped/Failed). A new `SuggestionService.set_imdb_identifier()` mirrors `apply_imdb_metadata_refresh()`'s field-preserving shape but narrower still -- it only ever adds the identifier (refusing outright if one is already set), never touches title, so it never needs the dict re-keying `edit_suggestion()`/`apply_imdb_metadata_refresh()` require. If the identifier saves but the immediate `refresh_one()` enrichment step itself fails (e.g. a title-collision edge case identical to Refresh's own documented one), the outcome is still reported Matched -- Recovery's contract is attaching the identifier, not guaranteeing every field lands in the same session; a future Refresh IMDb Metadata run picks up the rest. Architecturally, Recovery's biggest departure from Refresh is that every step is its own separate, interactive Discord event (a button click, a select, or a modal submit) rather than one long automated batch loop -- so unlike `perform_imdb_metadata_refresh`'s progress-edit throttling/pacer machinery, there is no equivalent needed here: each screen's own "Recovering N / M" header line IS the progress update, naturally paced by how quickly a person can review it, and only `start_imdb_recovery_session`'s own first inner transition (immediately after Start Recovery's ack) needs the `edit_original_response`-after-`response.edit_message` two-step Refresh's progress loop already established -- every subsequent screen is a fresh interaction using a single, ordinary `response.edit_message`. New `services/imdb_metadata_recovery_service.py` (the Discord-free core: discovery, search/matching including the year-mismatch fallback, save-then-refresh via composition over `ImdbMetadataRefreshService`, summary aggregation) and `imdb_recovery_view.py` (scope/confirmation/Crew-Review/match-selection/Search-Again-modal screens, deliberately not sharing view classes with `imdb_refresh_view.py` even where a button would look identical, keeping the two workflows unambiguous down to their custom IDs); new tests: `test_imdb_metadata_recovery_service.py` (19 tests: discovery, year-scoped/fallback/technical-failure search branches, accept-match save-then-refresh including fetch-cache dedup and the enrichment-failure-still-Matched case) and `test_imdb_metadata_recovery_command.py` (34 tests: scope/confirmation, single/multiple/zero-match screens, Search Again with both query formats, match-selection-then-Accept, Cancel Recovery, post-sync integration, progress header, final summary with the same oversized-breakdown-as-file fallback Refresh uses, idempotency, and cross-guild isolation) -- both files' fake OMDb `fetch_json` doubles dispatch on the request URL's `s=`/`i=` query parameters to serve search vs. title-resolution responses from one callable, mirroring how `test_imdb_metadata_refresh_service.py`'s `make_fetch` already worked for resolve-only requests. `test_database_manage_command.py`/`test_database_admin_view.py` gained the new button to their existing exact-custom-id-set/ordering/style assertions, same as Refresh's own addition did. Earlier work: **IMDb Metadata Refresh**. A new Crew-only `/database manage` action, **Refresh IMDb Metadata**, re-fetches already-persisted IMDb-derived fields (canonical title, plot, poster, runtime, genres, IMDb rating, MPAA/content rating, director, cast) for suggestions that already carry a usable IMDb link -- the answer to a gap this project has been documenting since `cast` was added (see "Shared Filter Menu" milestone below): older suggestions predating a given field simply never had it, with no way to backfill it short of re-adding them. Scope is **Refresh This Collection** or **Refresh All Collections** (every *active* collection in the *current* guild only -- `services/imdb_metadata_refresh_service.py`'s `resolve_refreshable_databases()` is the one place that guild/active filtering happens, so "all collections" can never leak across a guild boundary even on a WASH process hosting several servers), always gated behind a confirmation screen (scope, collection count, eligible-suggestion count, and explicit disclosure that external IMDb/OMDb requests will be made) before any request is made. The new `ImdbMetadataRefreshService` is deliberately Discord-free -- it depends only on `SuggestionService` and reuses the exact same `ImdbMetadataService` instance `/add`'s own `SuggestionInputService` already uses (now exposed via a new public `imdb_metadata_service` property, so no second, parallel metadata client exists), taking an optional `post_sync` callback so Discord-specific post-refresh concerns stay entirely in bot.py's `perform_imdb_metadata_refresh`. Lookups are strictly sequential and deduplicated by canonical IMDb title URL across the *entire* operation (not just per-collection), each unique title fetched at most once and reused for every matching suggestion, though each suggestion is still independently merged, persisted, and reported; a failed lookup gets one bounded retry (mirroring `sync_suggestion_status_embed`'s own existing retry convention) before being counted Failed. Merge behavior deliberately favors preserving existing data: a freshly-fetched response's `None`/absent field never overwrites a suggestion's existing valid value for that field -- only genuinely different, present values are applied -- and a suggestion whose merged fields are byte-for-byte identical to what's already stored is reported Unchanged and is never re-persisted (no wasted `updated_at` bump, no needless post-sync). `SuggestionService` gained `apply_imdb_metadata_refresh()`, `edit_suggestion()`'s sibling: like it, it re-keys the internal suggestions dict when a refreshed canonical title changes, refusing (never silently overwriting) if that would collide with a different suggestion's title already in the same collection -- a real, tested edge case (two distinct suggestions sharing one IMDb ID within the same collection inevitably resolve to the identical canonical title; the second to apply is correctly reported Failed rather than corrupting the first). `sync_suggestion_status_embed` (previously `-> None`) now returns a `SuggestionPostSyncResult` enum (`NO_POST`/`SYNCED`/`FAILED`) -- a fully backward-compatible change (every one of its ten existing call sites already ignored the return value) that lets the refresh workflow report post-sync failures separately from the metadata update itself, which is never rolled back on a post-sync failure. Progress reporting is intentionally two-layered: the service calls `on_progress` after every suggestion and at every collection boundary (as often as is genuinely useful), while bot.py's own callback throttles actual Discord message edits to collection boundaries or a minimum interval between per-suggestion updates (a real bug caught here during testing: the throttle's `last_edit_at` must be initialized to the loop's current monotonic time, not `0.0`, or the very first per-suggestion progress event always bypasses the throttle since the event loop's clock is not zero-based). The final summary includes a per-collection breakdown for Refresh All Collections, moved out to an attached text file instead of shown inline whenever it would push the message over Discord's 2000-character limit. Not a persistent/resumable job -- restart safety instead comes from every successful persist already being durable the moment it happens (no separate "in-progress" state to corrupt) and the operation being fully idempotent (a second run over the same data reports Unchanged, never duplicates a record or a post). Individual-suggestion refresh was deliberately not added to this milestone (out of scope per the task) -- audited `/suggestion edit`'s existing `EditSuggestionActionView` (Change Status / Move to Another Collection / Cancel) as the natural, minimal-effort future home for a fourth "Refresh IMDb Metadata for This Suggestion" button reusing this same service. New files: `services/imdb_metadata_refresh_service.py`, `imdb_refresh_view.py`; new tests: `test_imdb_metadata_refresh_service.py` (pure business logic: dedup, merge, skip/fail, guild isolation, idempotency), `test_imdb_metadata_refresh_command.py` (the full Discord-facing flow: scope/confirmation screens, permissions, cross-guild isolation, progress throttling, the final summary's attachment fallback, post-sync integration, command-level idempotency); `test_database_manage_command.py` gained the new button to its existing exact-custom-id-set/ordering/style assertions. **Follow-up (rate-limit friendliness):** live testing surfaced repeated Discord 429s on `PATCH /channels/{id}/messages/{id}` when many refreshed suggestions in the same channel had their posts resynced back-to-back. `perform_imdb_metadata_refresh` now paces those edits with a new, deliberately narrow `_ChannelEditPacer` (a per-channel minimum-interval tracker, `IMDB_REFRESH_POST_EDIT_MIN_INTERVAL_SECONDS = 1.25`) -- scoped to this one bulk workflow rather than `sync_suggestion_status_embed` itself (every other caller edits at most one post per user action, never in bulk), and only inserted before an edit that would land too soon after the previous edit to the *same* channel, since Discord's message-edit rate limit is bucketed per channel; edits to different channels are never paced against each other, and a suggestion with no existing post to sync never triggers a wait at all. `perform_imdb_metadata_refresh` gained an injectable `sleep` keyword parameter (default `asyncio.sleep`) purely so tests can assert pacing occurred without any real waiting -- four new tests in `PostEditPacingTests` (`test_imdb_metadata_refresh_command.py`) cover same-channel pacing, cross-channel non-interference, no-existing-post skipping the wait, and that totals/persistence are unaffected. Discord's own retry-after handling is unchanged and still applies as a fallback for whatever 429s still occur; this only reduces how often that fallback is needed, and metadata persistence remains fully independent of post-sync/pacing outcome. - `OMDB_API_KEY` (optional, enables IMDb-link metadata resolution)

Restricted commands fail closed when the relevant role is not configured by either method. See the [Installation Guide](09-Installation-Guide.md) for the full setup walkthrough.

## Architecture Rules

- Domain models own validation and business rules.
- Services coordinate application logic.
- Discord commands and views remain thin.
- Repository classes isolate persistence.
- Configuration is preferred over hardcoded community policy.
- Discord objects do not enter the domain layer.
- Guild-owned data and operations must remain guild-scoped.
- Historical records should be preserved rather than destructively replaced.
- Statistics are always derived from historical data, never maintained as running counters.

## Known Technical Debt and Limitations

- JSON is the current persistence layer; the specification still anticipates a future migration path to a more scalable database.
- A suggestion's six display statuses are Available, In an Active Vote, Pending Crew Review, Vote Winner, Watched, and Retired -- `WatchItemStatus.VOTE_WINNER` is set automatically when a voting round completes; a group's actual viewing is separately confirmed through the watch-history workflow; Pending Crew Review is reached via the "I Won't Watch" threshold and resolved by WASH Crew (Retire/Keep Active/Reset Rejections).
- Configurable scheduled-backup *execution* is not yet wired to the existing interval/retention settings (manual `/maintenance backup`, `/database backup`, and pre-destructive-action safety backups all work today).
- The richer Event Series/recurring-schedule/Discord Event model remains future work; scheduled watch parties today are single-occurrence.
- `SuggestionService`'s storage is keyed by `(database_id, normalized title)`, so two suggestions can never share an exactly-matching title within one database -- see [Administration](05-Administration.md)'s "Known limitation: identical titles within one database."
- Member/suggestion statistics that depend on a recorded submitter or creation date only cover suggestions added since FR-034 shipped; earlier suggestions are excluded rather than guessed at.
- Suggestions saved before public confirmation posts existed (or whose post failed at the time) have no original-post link for `/list` to show, and `/maintenance repair` cannot recover it -- Discord provides no reliable way to relocate a message after the fact without inventing a URL or risking a duplicate public post.
- `CHANGELOG.md`'s `[1.0.0]` entry is the release record; `[Unreleased]` tracks the release-candidate hardening work (suggestion status model, setup wizard redesign, vote editing redesign, duration syntax standardization) done since.
